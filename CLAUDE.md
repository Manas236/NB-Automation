# NB-Automation — Newsband Instagram post generator

Turns a newsband.in article into the standard red-template Instagram post (1080×1440 PNG).
Owner pastes article links into a local Flask dashboard and downloads the finished posts.

## Template layout (all constants at top of `make_post.py`)

- Canvas 1080×1440. Photo box `IMG_BOX = (20, 20, 1060, 1020)` (20px side gap, same as the originals), cover-cropped, only the **top-right** corner rounded (r=120). A 50px gap was tried and reverted at the owner's request.
- White logo pill `LOGO_BOX = (722, 1034, 1040, 1096)`; yellow dotted rule at y=1068 from x=60–700.
- Headline: Poppins Bold, white, left x=60, wrapped to 960px, **auto-sized**: starts at 76px and shrinks (min 40) until it fits in ≤3 lines and within y 1110–1345; block is vertically centred there. Straight quotes → curly.
- Footer: globe icon at (62,1355)–(126,1419) + underlined Poppins Regular 29px "For the complete story, click the link in the bio."

## Scraping newsband.in (`scrape_post.py`)

- Article pages: `https://www.newsband.in/article_detail/<slug>`. **Unknown slugs 200-redirect to `/index`** → the scraper rejects any response whose final URL lacks `article_detail`.
- Headline = the `<h2>` immediately before the main `<img>` (`.maan-post-img img`, src contains `uploads/blog_main_img/`). The page has other `<h2>`s (Categories, Related Posts…) so don't take the first one. Fallbacks: `og:title` / `og:image`.
- Image: the page shows `uploads/blog_main_img/<hash>_1.<ext>` (wide, e.g. 1200×650). The owner wants the `_2` version, which lives in a **different folder**: `uploads/blog_feature_img/<hash>_2.<ext>` (tighter crop, e.g. 850×650). `variant_url()` swaps both the folder and the suffix (zero-padding preserved). Not every article has a `_2` (e.g. Thane human-chain article) → falls back to `_1` and reports which was used.
- **Intro / "first line"**: `article_intro(paragraphs)` takes the paragraphs `article_body()` already extracted (dateline stripped) and cuts the first one longer than 20 chars to its first sentence (`first_sentence()`, abbreviation-aware: Dr./Rs./Mr.…). It used to walk `<p>` tags itself and returned `""` for every story whose body is bare `<div>`s — which is most of them; `where-is-the-road` reached Instagram with an empty intro that way (fixed 2026-09-22). Don't reintroduce a second body parser here: one extractor, one set of paragraphs. **Some stories repeat the headline (and a `By <name>` byline) as the body's first lines** — `article_body(soup, headline)` drops those leading lines (`same_text()` = case/punctuation-insensitive compare, `BYLINE_RE`) before dateline detection, and `article_intro(paragraphs, headline)` skips a sentence equal to the headline as a second guard. Before this (fixed 2026-09-24) 5 of 16 checked sitemap stories had intro == headline and lost their dateline. Shown with a Copy button in both the dashboard result card **and the gallery**; **never drawn on the post image** (owner's call).
- **Headline/intro are persisted**, via `save_meta()` → `meta/<slug>.json`, because the PNG carries neither and the poller has no UI to show them in — without this the intro was scraped and silently thrown away on every automated post. The gallery shows the real headline + intro when a sidecar exists and falls back to the filename slug when it doesn't (posts made directly by `make_post.py`, or predating the sidecars).
- Requests use a desktop UA header; site blocks nothing else.

No auth. `allow_firewall.bat` (run as admin) removes a pre-existing Windows Firewall *block* rule for python.exe on the Private profile and allows TCP 5000 — Claude cannot elevate, the owner must run it. `start_dashboard.bat` launches the server.

## Retention policy for `downloads/` and `output/`

Both folders grow unbounded otherwise (a real problem once sitemap-polling auto-detection lands). Fixed via `prune_dir(directory, keep=15, trigger=30)` in `make_post.py`:
- Once a folder reaches 30 files, the oldest 15 are deleted, leaving the 15 most recent — so at any given point at least the 15 most recent posts/photos are always available.
- Below 30 files, nothing happens (no constant trimming, just a periodic batch cleanup).
- `make_post()` calls `prune_dir(OUT_DIR)` after saving — but only on its default auto-named output path (`out_path=None`); an explicit `-o`/`out_path` (e.g. template-test renders `output/_t*.png`, or a batch CSV's custom `out` column) is left alone, so manual/test renders are never swept up.
- `download_image()` in `scrape_post.py` calls `prune_dir(DL_DIR)` after every save, unconditionally — `downloads/` has no manual-output escape hatch, it's only ever scraped photos.
- Both the dashboard (`app.py` → `process()`) and the CLIs go through these same two functions, so pruning applies everywhere posts/photos get created, with no separate cron/scheduler needed.

## Autopilot: detect → post, unattended (`poll_new_articles.py` + the thread in `app.py`) — live since 2026-09-18

Owner's target state: **keep `app.py` running and the whole thing runs itself** — sitemap → scrape → render → hashtags → publish → the card shows up in the gallery. `app.py` starts `run_forever()` in a daemon thread, but **only in the reloader child** (`WERKZEUG_RUN_MAIN == "true"`): the parent also executes the module, and two loops would race over `seen_urls.json` and double-post.

Source of truth is the **Google News sitemap** `https://www.newsband.in/news-sitemap.php`: XML, `<url><loc>` + `news:title` + `news:publication_date`, newest-first, ~30–35 entries covering roughly the last day. The poller diffs `<loc>` against `seen_urls.json`, keeps what was published **today** (IST, fixed +05:30 — not the PC's clock) and runs `process()` + `publish_post()` on those, oldest first so posts go out in story order.

- **Pacing is the first rail (added 2026-09-19, after the suspension — see below).** **Inside the dashboard (since 2026-09-26) Create & post does not publish itself: it hands every rendered post to the dashboard's publish queue** (`autopilot.QUEUE = app.autopilot_enqueue`, set in the reloader child), the same queue the Post button uses, so posts go out one at a time `MIN_API_GAP` + `API_GAP_JITTER` (2–3 min) apart, interleaved in order with manual clicks. Queue sidecar blocks carry `"by": "autopilot"|"manual"`; the queue worker reports autopilot outcomes back via `autopilot.record_publish()`; counters go through `bump_day()` (locked read-modify-write on `autopost_state.json` — never hold a `day` dict across a pass, the worker writes it too); `cap_reached()` counts published **plus** autopilot-queued. Pause or switching to Create only pulls the autopilot's queued posts back out (`unqueue_autopilot()`; they keep `publish: auto` and are re-queued by `drain_pending()` on the next poll after resuming); **Cancel** on an autopilot post sets `publish: manual` so it is never re-queued. The old behaviour — publish one, hold the rest for a 30-min slot, release one per 15-min poll — is why only the first 1–2 stories went out and evening stories were dropped at midnight. Standalone CLI (no `QUEUE`) still uses `MIN_PUBLISH_GAP` = 30 min + `PUBLISH_JITTER` (0–5 min random) between any two publishes; `NB_MIN_GAP_MINUTES` only affects that path. `gap_remaining()` derives "when did we last call the API" from the **sidecars** (`published_at` / `attempted_at`, whichever is latest), not from memory — the Flask reloader restarts the thread on every code edit and an in-memory timer would reset to "safe to post now" each time. **Failed attempts count too**, so an outage is not hammered. A post that misses its slot is simply not published: it keeps no `instagram` block, so `drain_pending()` at the top of the *next* poll picks it up. Rendering is still fast (`MAX_PER_POLL` articles per pass); only sending is a drip, one post per slot.
- **Safety rails (all load-bearing — this posts to a live newspaper account with nobody watching):** today's articles only (`--all-dates` / `NB_TODAY_ONLY=0` to widen); `MAX_PER_POLL` = 10 *rendered* per pass (was 3), the rest wait for the next poll; `MAX_PER_DAY` = 10 published per IST day (Instagram's own limit is 100/24 h, but that limit is about volume and volume was never what got us suspended) — past the cap posts are still *generated*, just not published, so the owner can send them by hand; a URL is written to `seen_urls.json` **before** publishing, so a crash can never re-post it; `already_handled(url)` scans the sidecars so a story the owner already published by hand from the dashboard is skipped, not regenerated; `already_published(png)` re-checks the sidecar immediately before publishing.
- **Catch-up on start**: a code edit restarts the Flask reloader, which kills the thread — possibly between rendering a post and publishing it (this happened during the first live run). `run_forever()` therefore calls `catch_up()` before its first poll: it publishes posts made **today** that carry `"source": "autopilot"` in the sidecar and have **no** `instagram` block at all. A *failed* post is left alone (the owner's Retry button owns it) and a post the owner generated by hand is never touched — that is what the `source` marker is for.
- **`save_meta()` preserves an existing `instagram` block.** It used to rewrite the sidecar wholesale, so re-rendering a story erased the record that it was already live — with the autopilot that is a double post. Don't undo this.
- **Dashboard strip** (top of the page): on/paused/off, what it is doing right now, last/next check, made + posted + failed today, a **Log** button showing the poller's log ring, and **Pause/Resume** (`POST /autopilot/toggle`, backed by the `ENABLED` event). The page polls `GET /autopilot/status` every 10 s and reloads itself when `version` changes — but not while a manual publish is in flight, the Why? overlay or the log is open, or a form is submitting.
- **Two modes, switchable live from the strip (added 2026-09-19 at the owner's request — “sometimes I want to post them myself”)**: **Create & post** (`POSTING` set) renders and publishes; **Create only** (`POSTING` cleared) renders and stops — the card shows the ordinary *Post to Instagram* button. `POST /autopilot/mode {"post": bool}` → `set_mode()`, which flips the event, persists `autopilot_mode.json`, updates `STATUS["posting"]` and logs. `Options.post` is a property over `POSTING`, so `handle_article()` / `drain_pending()` see the new mode on the very next article without a restart. Posts rendered in Create-only mode get `"publish": "manual"` in the sidecar and **`pending_posts()` skips them** — switching back to Create & post must never drip out a backlog the owner deliberately left unpublished; only `"publish": "auto"` posts (rendered while auto-posting, then cut off) are caught up. Switching *to* Create & post asks for a JS `confirm()`.
- Switches (all in `.env`, read at startup): `NB_AUTOPILOT=0` starts paused, `NB_AUTOPOST=0` starts in Create-only mode (until a mode is chosen on the dashboard — see `autopilot_mode.json`), `NB_POLL_INTERVAL`, `NB_MAX_PER_POLL`, `NB_MAX_PER_DAY`, `NB_TODAY_ONLY`, `NB_MIN_GAP_MINUTES` (0 disables pacing — don't).
- **Editing any imported `.py` restarts the poller** (stat reloader) and can cut a publish off mid-flight. Check the strip/log before editing; `--dry-run` and `--no-post` exist for testing.

- **There is no RSS/Atom feed and WebSub is impossible here.** `/feed`, `/rss`, `/rss.xml`, `/atom.xml` etc. all return **200 with the homepage HTML** (same catch-all as unknown `article_detail` slugs) — they are not feeds. With no real feed there's no `<link rel="hub">`, and WebSub needs the publisher to run a hub and ping it on publish, which this custom PHP site does not do. Polling is the only option; don't re-litigate this.
- **Why 15 min, and why that's the floor:** the sitemap is served through **Cloudflare with `Cache-Control: max-age=1800`**, so it's edge-cached for 30 min. That cuts both ways — frequent polling barely touches their origin (it's served from cache), but a new article can also stay invisible to us until that cache expires, so **detection latency is capped by their cache, not by our poll rate**. Polling faster than ~5 min buys nothing. Owner accepted "up to ~15 min late".
- **Don't bypass Cloudflare by hitting the origin IP.** It was considered and rejected: it removes the very caching that protects their origin (every poll would hit the PHP directly), origins behind Cloudflare usually refuse non-Cloudflare IPs anyway, the IP isn't stable, and it breaks TLS hostname verification.
- First live run (2026-09-18 16:13): 5 of today's articles detected, 4 generated and published automatically in ~4 min (the 5th was the one the owner had already posted by hand — correctly skipped). ~60 s per article end to end.
- Note: `robots.txt` sets `Content-Signal: ai-train=no` and disallows `ClaudeBot`/`GPTBot`/`Google-Extended` by name. The scraper's own `NewsbandPostBot/1.0` UA is **not** in that disallow list and `Allow: /` covers it, so current scraping is unaffected — but keep this in mind before pointing any AI-labelled crawler at the site.

## Hashtags (`hashtags.py` + `tags.yaml`) — V1 working

Per-article hashtag suggestion (≤5), shown on every dashboard card with Copy and a **Why?** overlay (candidate table: score, type, source/tier, evidence span, score factors, drop reason), persisted in the meta sidecar. Design was argued out over several rounds with the owner; the load-bearing decisions:

- **Formulation is article → candidate relevance, not article → category → filter.** The site's `.news_category` label is a *weak boost* via `config.category_map`; blank / `Trending` / unmapped labels give no signal. No topic-classification stage exists — topic tags are just candidates.
- **Evidence invariant (non-negotiable): a specific tag needs an evidence span in the text** — a catalogue alias/trigger, or a descriptive reference resolved under the rules below. No transitive inference ever: `Thane ↛ #TMC`, `politician ↛ party`, `location ↛ government body`, `crime ↛ #Police`. The catalogue's only edges are `parent` edges, which **generalise** (`#SlumRedevelopment → #CivicIssues`) and are used to *back off* under weak evidence, never to specialise.
- **Descriptive references** ("the civic body", "police", "state government") resolve in order: (1) exactly one entry with that `role` is explicitly named in the article; (2) the dateline place is in the group's `by_place` map; (3) otherwise the `generic` tag (`#CivicIssues`, `#Police`). Resolved evidence scores below explicit mention.
- **Candidate sources**: catalogue alias/trigger matches (longest-match, acronyms case-sensitive) → descriptive resolution → spaCy PERSON/ORG not in the catalogue (a bare headline surname is linked to the full name found later; ORG prefix variants merged) → semantic retrieval of topic entries by embedding (z-score over the catalogue + absolute floor, tier 2) → headline/lede noun chunks (tier 3; single words only as headline proper nouns, ≤3 tokens, bland adjectives stripped).
- **Scoring**: one additive function, `WEIGHTS` dict at the top of `hashtags.py`. Headline (+3), dateline (+2), lede (+1.5) dominate because articles are ~230 words (median; measured). Dependency role in headline/lede: subject +1, object +0.4, locative −0.6 ("… in Thane"). Frequency is weak (+0.3/extra mention, cap 3). Semantic z adds up to +1 for topic tags; a *negative* z penalises a topic whose trigger appears but which the story doesn't read like (not for headline hits). `weak_triggers` ("shot", "fire", "company") only count when semantic z ≥ 0.5 — this is what separates "actor shot in Thane" (crime) from "actor shooting a film in Thane".
- **Hard filters**: unknown (non-catalogue) PERSON → only if in the headline, and **never when a `sensitive` topic (crime family) has explicit evidence**; unknown ORG → only headline or lede subject; numeric chunks dropped.
- **The crime guard does not trust spaCy's PERSON/ORG label** (2026-09-22): `en_core_web_sm` types many Indian names as ORG — a murder victim and an accused came through as ORG and only the org zone filter held them back. In crime context, any unknown ORG that `looks_like_person()` is dropped, and so is an ORG containing a word of such a name (a shop named after the accused). Deliberately generous: single-word unknown ORGs count as names, so a non-catalogue place like "Turbhe" is dropped on crime stories too; the remedy is a catalogue entry, not loosening the guard.
- **Bare-surname aliases don't cross people** (2026-09-22): a person's `weak_aliases` surname right after a *different* given name ("Sahil Mhaske", an accused) is someone else. `other_given_name()` skips those matches — and all bare mentions of that surname in the same story — so they neither count as evidence for the catalogue politician nor claim the span from NER.
- **Selection**: MMR (λ=0.7, embedding cosine between candidate labels, ≥0.9 for ancestor pairs) with per-type caps (`TYPE_CAPS`: 2 person/org/place, 3 topic, 1 phrase) and a relevance `FLOOR` (2.0) — **fewer than 5 tags is the intended outcome for weak stories**; no fixed slots. `config.pad_to_five` + `brand_tags` pad with always-true tags only if the owner turns it on (off by default).
- **Not in V1, deliberately**: TF-IDF, YAKE, coreference, a topic classifier, learned weights, per-article web lookups, any LLM. Custom training only if the eval shows a ceiling.
- **Tuning goes through `eval/`** (built 2026-09-22; see `eval/README.md`). 27 frozen articles in `eval/corpus/`, ground truth in `eval/labels.yaml` (must/accept/forbid + the owner's editorial rules R1–R8/P1–P3 in its header), 18 dev / 9 **holdout — sealed, never label or run it until tuning is finished**. `eval/baseline.json` is the frozen pre-fix output; don't overwrite it. `eval/DIAGNOSIS.md` holds the diagnosed causes and the fix plan (#1 safety — done; #2 catalogue taxonomy — done; #3 catalogue gaps; #4 ranking). Measure every change with `python eval/run.py` and save a snapshot in `eval/snapshots/`. Don't tune `WEIGHTS`/`FLOOR` by intuition — the eval showed most misses and wrong tags come from `tags.yaml`, not weights.
- Runtime: spaCy `en_core_web_sm` + `sentence-transformers/all-MiniLM-L6-v2`, both lazy-loaded once per process (~5–10 s first call, then well under a second per article). Deterministic on the same machine. Model loads print nothing (HF progress bars disabled) so the Flask log stays readable.
- Scraper additions for this: `article_body()` returns (dateline, paragraphs, category) — body text comes from `.maan-card-body .maan-text` (author/date `.row` removed) because some stories have no `<p>` at all. Paragraphs are split on `<br>` and block-tag ends only, **not** on every text node: the old `get_text("\n")` chopped sentences wherever a story had an inline tag ("…unique theme at Sector" | "4, Sanpada"), which truncated both the intro and the hashtag system's input (fixed 2026-09-22). Dateline may be its own line and uppercase (`NAVI MUMBAI:`) or a foreign `Samarkand (Uzbekistan):` — `DATELINE_RE` allows parentheses, and the word-capitalisation that fixes `NAVI MUMBAI` only runs when the dateline is all-caps, so `(Uzbekistan)` isn't lowercased. `scrape_article_full()` returns the dict; `scrape_article()` still returns the old 3-tuple. `process()` calls `suggest_hashtags()` inside try/except — a hashtag failure is stored as `{"error": …}` in the sidecar and never blocks the post.
- Bash tool gotcha hit twice this session: long `python - <<'EOF'` heredocs containing triple-quoted strings hang the shell (python waits on stdin forever). Write patch scripts to the scratchpad and run them by path instead.

## Instagram publishing (`Insta_poster.py` + dashboard button + autopilot) — live

Owner has Instagram App ID/secret, account id, an access token (Instagram-Login style), **a Cloudinary account** (`di9mr0660`) and an imgbb key. Publishing happens two ways, through the same `publish_post()` code path: the per-card button, and the autopilot (which the owner asked for on 2026-09-18 — it does post by itself now).

- **Image hosting: Cloudinary primary, imgbb fallback.** Meta's image API has *no upload endpoint*: `POST /{account}/media` only takes an `image_url` it downloads itself, JPEG only. So the poster converts the PNG to JPEG in memory, uploads it (signed upload to `api.cloudinary.com/v1_1/<cloud>/image/upload`, folder `newsband-ig`, public_id suffixed with a timestamp), hands Instagram that `secure_url`, and **deletes the copy again right after publishing** (`delete_hosted()` → `image/destroy`; `NB_IMAGE_KEEP=1` keeps it). Hosts are pluggable behind `NB_IMAGE_HOST` / `NB_IMAGE_HOST_FALLBACK` — if container creation fails with a *fetch* error (`_is_fetch_failure()`: code 9004 / subcode 2207052 / “could not be fetched”) the same JPEG is re-uploaded to the other host and the post is retried once. **The dashboard stays LAN-only. Never propose tunnels / `NB_PUBLIC_BASE_URL` / public binding again** — a first version did that and the owner was (rightly) furious; it has been removed.
- **Don't call either host “blocked”.** imgbb failed every attempt on 2026-09-17 (9004/2207052 on `i.ibb.co`) and the owner published through it successfully on 2026-09-18; the failure is intermittent on Meta's side. Saying otherwise got an explicit “don't give unreliable data” from the owner. That intermittency is exactly why the fallback exists.
- **Every publish is paced at the source (added 2026-09-21).** `Insta_poster.MIN_API_GAP` (120 s, `NB_API_MIN_GAP_SECONDS`, never below 60) is a hard floor between *any* two Instagram API attempts — `publish_post()` and the CLI `post` raise `PacingError` (nothing sent, nothing written to the sidecar) if `api_gap_remaining()` says the last attempt (per the sidecars, via `last_api_attempt()` — now lives here, the autopilot delegates to it) is too recent. The owner spotted the hole: in Create-only mode, spam-clicking *Post to Instagram* on card after card reproduced the 20–30 s burst that caused the suspension. So the **dashboard button no longer publishes directly — it queues**: `POST /instagram/post/<file>` writes `{"status": "queued", "queued_at"}` to the sidecar, appends to `app._queue`, and replies 202; one `queue_worker` thread sends the head after `MIN_API_GAP + random(0, API_GAP_JITTER=60 s)` — i.e. clicks go out **2–3 min apart, in click order**. The card shows *Queued · sends at about HH:MM / position N* with a **Cancel** button (`POST /instagram/cancel/<file>` → `dequeue_publish()` restores the previous block, or none). The queue survives a reloader restart: `requeue_from_sidecars()` (reloader child only) re-queues every `status == "queued"` sidecar by `queued_at`. The strip shows *N manual posts queued, next at about HH:MM*. `pending_posts()` skips queued posts (any `instagram` block does). The autopilot treats a `PacingError` (a manual post just went out) as a HOLD, not a failure; its own 30-min gap sits on top of the floor and `NB_MIN_GAP_MINUTES=0` now still leaves the floor.
- **A post with no caption content is not postable (added 2026-09-22).** `Insta_poster.caption_problem(meta)` returns why a post is not ready (`""` when it is): no `intro`, a hashtag `error`, or an empty `tags` list — i.e. exactly what `build_caption()` needs. `publish_post()` raises `IncompleteError` (an `InstagramError`, `step="incomplete"`) **before** the pacing check, sends nothing and writes nothing to the sidecar; the dashboard endpoint answers 400 before queueing; the card shows *Not ready: …* and the hint instead of the button (`instagram_view()` adds `ready`/`not_ready`, mirrored in `renderIg()`); the autopilot's `publish()` logs `NOT READY` and declines, and `pending_posts()` filters incomplete posts out so one can never stand at the head of the drip queue and block everything behind it. `build_caption()`'s headline fallback stays for the CLI, but nothing reaches it by that route any more. The cure for a flagged post is to re-generate it from its article link, not to override the gate — there is deliberately no force path. (Found because `where-is-the-road.png` went out with an empty intro.)
- **Flow**: card **Post to Instagram** → JS `fetch POST /instagram/post/<file>.png` → queued (above) → `queue_worker` calls `insta.publish_post(png_path, force)` (the autopilot calls the same function) → caption from the sidecar → image host upload → `POST /{account}/media` → poll `GET /{container}?fields=status_code` until `FINISHED` → `POST /{account}/media_publish` → `GET /{media}?fields=permalink`. Result merged into the sidecar as `meta["instagram"]` via `scrape_post.update_meta()`; the card redraws itself from the JSON reply (no page reload).
- **Sidecar block**: `{"status": "queued", "queued_at"}` while waiting in the dashboard queue (plus the earlier `media_id`/`permalink`/`published_at` on a repost); `{"status": "published"|"failed", "media_id", "permalink", "container_id", "published_at", "image_url" (the imgbb URL), "caption"}` on success; `{"status": "failed", "error", "step" (upload | create container | container status | publish), "attempted_at"}` on failure (a failed *repost* keeps the earlier `media_id`/`permalink` so the card still shows the live post); `previous_media_ids` accumulates on explicit reposts. Tokens/keys never reach the sidecar — every `InstagramError` message goes through `redact()`.
- **Duplicate protection**: `status == "published"` → endpoint answers 409 unless `?force=1`; the card shows **Post again** (JS `confirm()`) instead of the post button. A post already in the queue answers 409 too (the old `_posting` in-flight set is gone — the queue is the guard). **Retry** after a failure is a plain re-post (`force` only when an earlier publish exists).
- `is_configured()` = `not configuration_error()`: Instagram credentials **and** the active host's credentials; `configuration_error()` returns the one-line reason the UI shows (the template and the `/instagram/post` 400 both use it, so no message names a specific host any more). `config()` itself only needs account id + token, so `check` and `post <https-url>` work without any image host. `.env` is read at import (python-dotenv) — the Flask reloader does not watch it, restart after editing.
- **Hosts**: default `graph.instagram.com` (`INSTAGRAM_API_HOST`), version `v26.0` (`INSTAGRAM_API_VERSION`; v26.0 is the latest as of 2026-09). `graph.facebook.com` is supported for Facebook-Login tokens and then `appsecret_proof` is added automatically. `INSTAGRAM_APP_ID` is not used by any call; `INSTAGRAM_APP_SECRET` only for the proof.
- **Verified against the real API on 2026-09-18**: Cloudinary upload → container → publish → permalink → hosted copy deleted, from both the dashboard and the autopilot. **The template's 3:4 (1080×1440) image is accepted** — the old 36003 aspect-ratio worry is settled, no padding needed in `to_jpeg_bytes()`. Container creation takes ~10 s, the whole publish ~25 s.
- Caption format = first line (intro, with any leading `Place:` dateline removed by `scrape_post.strip_dateline()`), blank line, hashtags **lowercased** and joined by spaces; trimmed to 2200 chars. **No headline** (owner's call, 2026-09-17 — it's already on the image); the headline only stands in when the sidecar has no intro. Posts without a sidecar (made by `make_post.py` directly) get the filename slug as caption and no hashtags. Lowercasing happens only in `build_caption()`; the sidecar and dashboard keep the catalogue's casing.
- Rate limit reminder: 100 API-published posts per 24 h per account.

## The suspension (2026-09-19) — read this before touching publish cadence

Meta suspended the account's API access. Every Instagram endpoint, including a read-only
`GET /me?fields=id,username`, returns `API access blocked.` / code 200 / no subcode, on every API
version. Not a token problem (expiry is code 190, and the token still parses), not dev-vs-live
mode (13 posts published fine the day before on the same app and token, and dev mode fails with a
named-permission error instead), not Cloudinary, not the 3:4 aspect ratio.

**Cause: cadence, not volume.** On 18 Sep the autopilot published 19 posts in ~2.5 h, in runs of
five spaced **23–32 seconds** apart — that spacing is just the pipeline's own publish latency, so
it was machine-regular, on a brand-new integration's first day. `MAX_PER_POLL = 5` with no delay
between publishes made that the *intended* worst case. The caps guarded posts-per-day and never
looked at posts-per-minute.

Rules that follow from it:
- **Never publish two posts back to back — from any path.** `Insta_poster.MIN_API_GAP` is the floor
  for everything (button queue, autopilot, CLI). In the dashboard the autopilot feeds the button's
  queue (2–3 min apart, owner's call on 2026-09-26); the CLI's 30-min gap sits on top there. Leave both on.
- A daily cap is not a rate limit. Meta's documented 100/24 h is about volume and says nothing
  about how bot-like the timing looks; their integrity systems are a separate thing entirely.
- Jitter matters as much as the gap. A post exactly every 30 minutes is still a machine signature.
- Recovery is the owner's to do (App Dashboard banner / appeal); no code change restores access.
- While access is suspended, `.env` has `NB_AUTOPOST=0` so the poller keeps generating posts for
  manual publishing and stops calling a suspended API. Remove it once access is back.
